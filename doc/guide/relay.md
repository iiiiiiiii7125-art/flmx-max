# 对接中转

**中转** 页的 **线路** 标签按落地列出所有中转线路，点一个落地 → 选择隧道即可添加（也可以在落地页点入站 → **中转**）。隧道在 **中转** 页的 **隧道** 标签创建，入口是中转机；原来的“规则”在 **规则** 标签。隧道质量在 **质量** 标签查看。

## 对接方式

- **端口转发**：中转机直接把流量转发到落地机的公网地址
- **隧道转发（出口为落地机）**：流量经隧道到落地机，再转发到 `127.0.0.1:入站端口`。入站可以只监听 `127.0.0.1`，落地机不对外暴露端口
- **隧道转发（出口为其他节点）**：用于“前置 → IX → 落地”这类多跳线路。流量经隧道到出口节点（如 IX），再由出口节点连接落地机的公网地址。只需要中转、不需要加密时，隧道协议选 TCP 即可

## 前置 → IX → 落地

1. 节点页添加前置、IX、落地三台机器，都装好 agent
2. 隧道页新建一条“隧道转发”：入口选前置，出口选 IX，协议按需选择（不需要加密就选 TCP）
3. 点击落地机上的入站 → **中转**，选这条隧道
4. 如果 IX 只允许前置访问，在 IX 的防火墙里放行前置的地址即可；落地机可以开启入站白名单，只放行 IX

订阅里的中转线路使用前置的地址和入口端口。

## 链中某一跳故障时：明确断开，不再静默绕行

1.3.4 起，多跳链（隧道链 / 链式代理的节点侧链路）中**任一跳的全部节点不可用时，连接会明确失败并报错**（错误信息带链名，可定位是哪条链断了）：

- 旧行为是中间跳故障时静默截断、绕过后面的跳继续走，首跳故障时甚至静默变成从本机**直连**出站——连接看似可用，实际出口与预期不符，还可能暴露真实出口 IP；
- 新行为下链部分故障期间受影响的连接直接断开，链恢复后自动正常；链健康时行为与之前完全一致。

这是有意的行为变更：静默直连属于隐私事故，明确失败才可观测、可告警。如果升级后出现「链断了才发现某跳长期故障」，按报错里的链名检查对应跳的节点即可。

## 订阅与清理

中转线路会自动加入订阅，名称为“隧道名 → 入站名”。删除中转、入站或内核时，相关的转发会一并清理。

## 用户分组与限速规则（用户页）

用户多、隧道多时，可以在 **用户** 页用分组批量管理分配权限：

- **用户组 / 隧道组**：把用户、隧道分别编组（**用户** 页 → **分组** 标签）。
- **组权限**：把某个用户组授权给某个隧道组，只是登记一条分配范围：之后给该组用户分配隧道时，可选范围就是被授权隧道组里的隧道，范围外的隧道会被拒绝并点名提示。组权限本身不会给任何用户发放隧道授权，也不会触发任何转发——用户最终能用哪些隧道，只由逐个分配的授权决定。分组是可选的批量管理工具，不分组的用户与隧道照常逐个分配；用户同属多个有组权限的分组时，可选范围是这些隧道组的并集；停用的分组不产生范围（既不约束、也不贡献可选隧道）。

**分组停用语义**：停用、重新启用或删除用户组 / 隧道组，撤销组权限，把用户移出分组或把隧道移出分组，都只影响之后分配时的可选范围，不会收回任何已经分配给用户的隧道授权，也不会清理其转发；重新启用分组也不会自动补发授权。已经分配的授权只通过用户页的分配操作增删。注意：升级到本语义之前由旧版组权限自动展开生成的授权（历史上称「组建授权」）同样保留、不会被追溯收回；如需收回，在用户页对相应用户逐条删除即可。

**限速规则**（**用户** 页 → **限速** 标签）是命名的速率上限（名称 + 速率），建好后被引用才生效：

- 转发可以分别绑一条**全局限速**（整条转发合计）和一条**单 IP 限速**（每个来源 IP 各一份）；
- 隧道本身不绑限速；在 **用户** 页把隧道分配给用户时，可以为这条分配选一条限速规则，该用户经这条隧道建立的转发按它限速（转发自己绑了全局限速时，以转发绑的为准）。

## 获取真实客户端 IP（仅 Xray）

开启后，中转转发会附带 PROXY protocol，落地机内核日志里能看到客户端真实 IP。开启后直连将无法使用，入站会自动变为“仅中转”。

## 入站白名单

开启后，该入站端口只放行本机、直接连接落地机的节点（端口转发的中转机、隧道转发的出口节点）和你填写的额外 IP / 网段，其余来源直接丢弃，只影响这一个端口。中转增删时白名单会自动更新。

## 删除隧道与节点离线时的语义

删除隧道**不需要节点在线**：节点离线 / 不可达时，在面板里删隧道会立即生效——隧道、挂在它上面的转发与用户分配在数据库里一并删除，接口直接返回成功（对已删除的隧道重复删除同样返回成功），节点侧残留监听等重连对账时清理（见下）。

但有一个例外：**节点在线、且删隧道前清理其名下转发的数据面时出现真实失败**（节点明确回失败等非离线错误）时，删除会**中止**——隧道不会被删（防止留下脱离面板计数的孤儿监听），接口返回失败回执，并且回执会**披露此前已实际删除的转发清单**（已删除多少条、名称 / ID；已删项不回滚）。撞见这种回执时，先按回执里点名的转发与错误处理节点侧问题，再重新删隧道；不要按「离线也能删」的口径预期它必然成功。隧道与转发的手动诊断入口与结果口径见 [监控 · 手动诊断](./monitoring.md#手动诊断)。

删除类接口有两种回执口径并存（有意设计）：**单个删除**（删隧道、删节点、删转发等）对「目标不存在」一律按已删处理、返回成功，重复删除与删后重试不会报错；**批量删除、删除预览、连同转发一起删除**这类复合操作则逐条给结论，目标不存在会明确报「隧道不存在」或计入失败明细，方便逐条对账。两种口径不要混读：单删的「成功」只承诺删完后该对象不存在，不承诺它删之前存在过。

节点侧监听的清理由 agent 在**重连对账**时完成：离线期间删掉的隧道，节点重新连上面板后会按面板的最新配置把对应监听撤掉，本机实测三方（数据库、节点监听、nft 规则）最终一致、无残留。

注意：如果节点其实没有停机、只是与面板**网络分区**（agent 还在运行、只是连不上），分区期间旧监听会继续按删除前的配置服务，直到分区恢复、agent 重连完成对账。介意这一点的场景，请先停掉节点 agent 再删隧道。

## 联邦（面板共享）升级顺序：先消费方，后提供方

1.3.4 起，提供方的 middle / exit 角色服务恒带每共享独立的 relay 鉴权凭据，旧版本消费方不带凭据会被拒绝。双方版本不一致时的行为：

| 组合 | 结果 |
|------|------|
| 新消费方 + 旧提供方 | 正常：旧提供方不下发凭据，消费方就不带凭据连接，旧的无鉴权服务照常接受 |
| 旧消费方 + 新提供方 | **中转链数据面不通**：消费方无凭据被提供方拒绝；但控制面（连接、建隧道、状态同步）全部显示成功，面板上看不出异常——只有流量不通 |
| 双方同为 1.3.4 | 正常，凭据自动下发与自愈 |

所以升级联邦双方时请按 **先消费方、后提供方** 的顺序：先升消费方不会产生任何断裂窗口；反过来先升提供方，断裂窗口从提供方升级那一刻就开始、一直持续到消费方也升完。无论哪种顺序，两方都应尽快升到同一版本。

**版本提示（panelVersion）**：1.3.4 起联邦连接（Connect）会互相携带面板版本号。消费方版本缺失或低于 1.3.4 时，提供方会在回执里给出 `versionWarning` 并记一条日志；消费方一侧在导入远端节点、用量同步、状态同步的回执里同样能看到对端版本与该警告。看到「对端面板版本过旧」类提示，含义就是对方还没有 relay 鉴权（或还没被鉴权保护），按上面的顺序尽快把落后的一方升上来即可。提供方若从旧备份恢复，存量共享的凭据会被重新补发，消费方在下次同步时自动自愈刷新，期间可能有短暂窗口。

## 联邦隧道的已知限制：对端可能残留孤儿隧道

（联邦在面板菜单里叫 **面板共享 / 共享**，是同一功能。）

通过联邦使用对端面板的节点建隧道时，面板先在对端创建隧道、再在本地保存。如果本地保存这一步失败（例如端口冲突或数据库异常），对端已经创建的隧道不会自动回滚，对端会残留一条没有本地对应记录的**孤儿隧道**，并占用对端的端口。

**这是已知限制，不是 bug。** 管理员需要定期检查对端面板的隧道列表：发现对端存在、但本地没有对应记录的隧道时，在对端面板手动删除它。另请注意：本地保存失败后，如果直接用同一端口重试建隧道，会被对端以「Port already in use」拒绝（孤儿隧道仍占用着该端口、不会自动消失），须先在对端面板手工清理孤儿、释放端口后再重试。
