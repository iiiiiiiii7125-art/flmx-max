# FIX-R18-F1-01-D3 — tunnel TLS peer authentication (D-3)

Finding: **R18-F1-01 (P1)** — panel-generated TLS/mTLS/WSS tunnel hops had
encryption but no peer authentication. The panel rendered chain dial configs
with no TLS block; the agent parsed an empty TLS block as an empty config;
`LoadClientConfig` set `InsecureSkipVerify = !Secure = true`; a listen side
with no cert file generated a random self-signed cert with no client-cert
verification. "mtls" did not actually exist: an on-path attacker could
impersonate the next hop and read/write that hop's traffic. (The agent→panel
WS control channel was verified unaffected — it verifies the peer.)

Decision: **D-3** (user, 2026-11-20): panel-distributed CA (unique per
install) + per-node certificates via the existing AES control channel; dial
side renders `tls {secure, caFile}`, listen side renders
`{certFile, keyFile, caFile}`; missing certificates = fail-closed, no
fallback to self-signed + skip-verify. Certificates must be distributed and
verified before switching rendering — running chains are never broken.

## Behaviour contract

- A node that was never issued certificates and cannot be reached stays
  not-ready and its segments keep the legacy (unverified) form — the
  running chain is never touched.
- The one fail-closed exception: a node that WAS issued certificates before
  but still has none after the re-issue attempt refuses the whole deploy
  (`tunnelTLSReadyForState` errors before anything is pushed), so a
  verified chain is never silently downgraded to unverified rendering.
- Old agents answer "unknown command" and therefore stay not-ready
  (legacy) until upgraded — unless they were issued certificates before,
  in which case the deploy fails closed and the operator sees why.

## Render-path contract (pinned by tests, not by shared code)

The agent-relative render paths `tls/ca.pem`, `tls/node-cert.pem`,
`tls/node-key.pem` are produced panel-side by `tunnelTLSAgentPaths()`
(`go-backend/internal/http/handler/tunnel_tls.go`) and must match the
agent's `tunnelTLSPathsForRender` (`go-gost/x/socket/tunnel_tls.go`).
The two modules do not share code; the contract is pinned by the render
tests in `audit_r18_f1_01_d3_test.go`. If either side renames a path,
update this record and the tests together.
